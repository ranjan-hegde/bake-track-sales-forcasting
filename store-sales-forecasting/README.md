# Nexus Sales Forecasting (Dual-Model: SVR + LightGBM)

A machine-learning system that forecasts **daily unit sales for newspapers and
magazines** from publication, demographic, temporal and recent-sales signals.
It trains **two models side by side** — Support Vector Regression (SVR) and
LightGBM — and exposes them through a FastAPI service.

> Domain: print-media sales forecasting (newspapers / magazines).
> Use it to anticipate demand, plan print runs, and reduce returns/stockouts.

## For the seller: pick a day, get a number

The web UI is built for a **small-town newspaper/magazine seller**, not for
comparing models. The workflow is:

1. **Pick any day** on the calendar and choose **one** model (LightGBM or SVR —
   your call).
2. The app **auto-detects** that day's context — weekend, season, and any Indian
   **holiday/festival** (e.g. Diwali, Holi) — so you never fill those in.
3. The app **auto-looks-up the sales history** for your publication + region
   (same date last year, else the most recent days on record) to fill the
   "yesterday / last week" figures for you. On a festival day it also surfaces
   what *past* festival days averaged, as an insight.
4. You get **one number**: how many copies you can expect to sell that day.
5. When the day is done, **record the actual sales**. The row is appended to the
   history and **both models retrain immediately**, so the next forecast learns
   from real data.

This is powered by `POST /forecast` and `POST /record-sale` (see below). The
`/predict` and `/compare` endpoints remain for programmatic / side-by-side use.

## Latest trained metrics

Held-out test set (20% split, 2,924 rows). Regenerated by the training pipeline
into `artifacts/model_metadata.json`.

| Model     | R²     | MAE    | RMSE   | Train time |
|-----------|--------|--------|--------|------------|
| LightGBM  | 0.7629 | 102.32 | ~128.0 | ~0.5 s     |
| SVR (RBF) | 0.5992 | 131.83 | ~166.4 | ~16 s      |

LightGBM is selected as `best_model` (lowest MAE). Numbers refresh every time
you retrain; treat the table as indicative.

## The 17-feature schema

Every prediction is built from these features (this exact column order is the
trained feature order, persisted to `artifacts/feature_names.joblib`):

`Publication_Name, Publication_Category, Region, Customer_Age, Income_Level,
Educational_Background, Occupation, Season, Day_of_Week, Is_Weekend,
Is_Holiday, Is_Festival, Special_Events, Promotion, Price,
Previous_Day_Sales, Previous_Week_Sales`

Temporal features (`Season, Day_of_Week, Is_Weekend, Is_Holiday, Is_Festival`)
are derived automatically from the target date — callers never supply them.

## Setup

```bash
git clone <your-fork-url>
cd store-sales-forecasting
python -m venv ml_venv && source ml_venv/bin/activate
pip install -r requirements-dual.txt
```

Optional runtime configuration lives in environment variables (see
`.env.example`): `ARTIFACTS_DIR`, `DEFAULT_MODEL`, `LOG_LEVEL`, `API_HOST`,
`API_PORT`, and `API_KEY` (set it to require an `x-api-key` header).

## Generate data & train

```bash
# 1) (re)generate the ~14,620-row synthetic dataset
python generate_dataset.py

# 2) preprocess + train BOTH models end-to-end, writing all artifacts
python -m src.pipelines.dual_train_pipeline
```

This produces `svr_model.joblib`, `lgbm_model.joblib`, `scaler.joblib`,
`encoders.joblib`, `feature_names.joblib`, `dual_model_results.json`, and
`model_metadata.json` under `artifacts/`.

### Endpoints

| Method | Path           | Purpose                                                        |
|--------|----------------|----------------------------------------------------------------|
| GET    | `/`            | Web UI (or JSON status if UI absent)                           |
| GET    | `/health`      | Liveness probe (always ok if process is up)                    |
| GET    | `/ready`       | Readiness probe (503 until models are loaded)                  |
| GET    | `/options`     | Allowed categorical values (from fitted encoders)              |
| GET    | `/metadata`    | Model version, metrics, library versions                       |
| POST   | `/forecast`    | **Seller:** one day → one number, with auto-detected context   |
| POST   | `/record-sale` | **Seller:** log real sales → append to history → retrain both  |
| POST   | `/predict`     | Forecast with a chosen model (`svr` or `lgbm`), manual lags    |
| POST   | `/compare`     | Forecast with BOTH models + their difference                   |

The seller endpoints need no manual sales history — just pick a date:

```bash
# Forecast one day (history + festival/holiday/weekend auto-filled)
curl -s -X POST http://localhost:8000/forecast \
  -H 'Content-Type: application/json' \
  -d '{"publication_name":"The Daily News","publication_category":"News","region":"North","promotion":0,"special_events":"None","target_date":"2025-10-21","model_type":"lgbm"}'

# Record the real sales for a day, then retrain BOTH models (~15-20s)
curl -s -X POST http://localhost:8000/record-sale \
  -H 'Content-Type: application/json' \
  -d '{"publication_name":"The Daily News","publication_category":"News","region":"North","promotion":0,"special_events":"None","target_date":"2025-10-21","actual_sales_quantity":812}'
```

`/record-sale` writes to disk and triggers training, so gate it in production by
setting `API_KEY` (it then requires the `x-api-key` header, as do `/forecast`,
`/predict`, and `/compare`).

## How a prediction is computed

1. **Assemble features** — user inputs + temporal features derived from the
   target date form one 17-column row.
2. **Encode categoricals** — the fitted `LabelEncoder`s map strings to integers.
   Unseen values fall back to `None` (or the first class) and are logged.
3. **Reorder & scale** — the row is put in the trained feature order and passed
   through the fitted `StandardScaler`.
4. **Model inference** — SVR sums kernel similarities to its support vectors;
   LightGBM sums the outputs of its gradient-boosted trees.
5. **Clamp** — negative predictions are clipped to `0` (sales can't be negative).

For the seller-facing `/forecast`, steps happen the same way, except the two lag
features (`Previous_Day_Sales`, `Previous_Week_Sales`) are **not** typed by the
user — `src/components/history_lookup.py` looks them up from the historical CSV
(same date last year, else most-recent days, else the publication+region mean).
On a festival day the lag stays a realistic baseline; the festival average is
returned separately as a display-only insight so the model's `Is_Festival` lift
isn't double-counted.
